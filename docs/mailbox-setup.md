# Shared support mailbox

## Everyday flow

1. Open any lead and click **Email**. Your saved draft opens if one exists; otherwise the **Support email** template opens.
2. Edit the message, choose **Change template**, or design blocks and **Save as template** for the project. **Save draft** preserves your own unfinished message.
3. Click **Send** deliberately. The configured shared sender delivers it and the company's outgoing history records the result.
4. Administrators use **Mailbox** for Inbox, Outbox, Sent and their private drafts. Researchers see incoming replies only on companies in their assigned projects.
5. Open an incoming message and **Reply**, or open its company and templates. An unmatched message must first be linked to a company; linking shares it with that project's team and records a response.

Connecting a mailbox does not send drafts. Draft funnels still require administrator activation. Existing recipient limits, suppression, named sender, opt-out and copy rules apply to replies as well as other emails.

## Connection

In **Workspace settings**, configure the outgoing SMTP submission host, username, password/app password, sender name/address and optional copy address. Set Reply-to to the inbox you intend to receive here.

Under **Incoming mail**, configure the provider's IMAP hostname, username, password/app password and folder (usually `INBOX`). TLS on port 993 is required. Enable automatic sync, save, then click **Verify & sync**. A successful sync verifies the connection without sending an email. Settings never return the password; it is encrypted with the workspace encryption key. Changing the host/account requires a new password. Disable sync and clear the password to disconnect incoming mail.

The account must permit IMAP password authentication. A provider-issued app password may be required. This release does not implement Google/Microsoft OAuth; an account that requires OAuth cannot connect through this password form. Provider identification and real credentials remain a deployment step. Do not put credentials in frontend environment variables.

## Sync and reply matching

- Initial sync imports the latest 20 messages from the selected folder. Subsequent minute-based syncs process up to 20 new messages at a time, scanning bounded UID windows. It is not a historical archive import. UID validity changes start another recent window; duplicate messages with the same ID, sender, timestamp and subject are not imported twice.
- Sync is read-only on the server. Read status is local to the app. Original messages, server read flags, folders and attachments remain unchanged.
- Only plaintext previews are stored. Sources larger than 512 KB show a notice instead of a body; text previews stop at 20,000 characters. Attachments remain in the original mailbox. No inbound HTML is executed or images downloaded.
- Replies automatically link only when their references match an unpredictable Message-ID generated by this app and their sender matches that message's recipient. Ambiguous/unreferenced mail stays in the administrator's inbox. Messages sent before this feature may need manual linking.
- Each linked reply appends an outreach event and notification. It can set **Replied** and stop applicable existing follow-ups, but does not overwrite Converted, Interested, Stopped or Unsubscribed, or a newer deliberate outcome. A historical reply does not stop a sequence created afterward. Qualification never changes.
- The worker checks incoming mail before due campaign deliveries. If incoming sync is enabled and fails, automatic delivery pauses until sync succeeds or an administrator disables incoming sync. No automatic conversion or interpretation of message instructions occurs.
- Outbox distinguishes pending, refused/blocked and unknown delivery attempts, plus scheduled campaigns. Unknown SMTP acceptance is never retried automatically. Sent means mailbox acceptance, not proof of inbox delivery. The Sent view includes messages sent by this app, not the provider's historical Sent folder.

## Implementation and verification

`server/imap.ts` uses [ImapFlow](https://imapflow.com/docs/api/imapflow-client/) for bounded read-only TLS access and [MailParser](https://nodemailer.com/extras/mailparser) for MIME-to-text previews. DNS addresses are validated and pinned; TLS certificate validation, connection deadlines, response/literal limits and disabled transport logs are enforced.

`server/mailbox.ts` owns encrypted incoming settings, single-flight synchronization, reply matching and administrator mailbox APIs. Project reply APIs recheck membership. Configuration revisions and the enabling administrator are rechecked after network work; obsolete results are discarded.

The disposable `tests/mailbox.test.ts` suite covers encryption, host changes, access/CSRF, synchronization races, duplicates, reply linking, terminal outcomes, threading, draft privacy, uncertain delivery and bounded parsing/UID progression. `tests/browser-preview.ts` supplies simulated mail for interface verification; it never accesses the real mailbox or database.
