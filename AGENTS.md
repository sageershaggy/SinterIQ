# Innovista Research AI

This is a project-based training, lead research and qualification workspace. Sintertechnik is one starter project, not the hardcoded identity of the platform.

## Product scope

- Projects, source libraries, training analysis, approved versioned rubrics, lead research, evidence-backed qualification, human review and history.
- Per-project team assignment, website-published business contacts, fit-score outreach bands with a call opener, lead-level training feedback, per-lead calling assignment and an append-only call log.
- A per-project Calls page and a light CRM layer on each lead: a manual lead status with its history, and team comments.
- One mailbox per project, with no workspace mailbox behind it: per-lead email composed from the qualification, sent deliberately from that project's own address, logged sent or refused.
- Project email funnels: up to three scheduled messages sent through the project's own mailbox, deliberate administrator activation, copy recipient, response history and recipient opt-out. No deals, commissions, orders or unrestricted bulk email blasting.
- Read README.md and docs/upgrade-review.md for architecture, migration and security details.

## Stack and commands

- React 19, TypeScript strict mode, Vite 8, plain CSS and Lucide.
- Express 5, better-sqlite3, Zod, Gemini or OpenAI-compatible AI.
- Node.js 22.16+.
- npm run dev: local app on 127.0.0.1:3000. The public page is always sign-in.
- npm run admin:init: server-side initial administrator provisioning with a unique generated password; refuses to overwrite any existing accounts.
- npm run lint, npm test, npm run build; npm run check runs all three.
- npm audit for dependency verification. Prettier configuration is included.

## Required invariants

- Every source, lead, run and training lookup is scoped to its project. Never query a child record by ID alone.
- All business APIs require authenticated server sessions. Never add default passwords, auth bypasses, browser credential storage or identity-header fallbacks.
- Sign-in has an Administrator and a Guest (researcher) portal. The portal is checked only after the password is verified, a wrong portal creates no session, and an unknown user or wrong password answers the same whatever the portal. The stored role, not the portal, is the access boundary. "Keep me signed in" makes a session last 30 days instead of 12 hours.
- Administrator rights use the persisted role. A researcher reaches only assigned projects; an unassigned project must answer 404 on every project-scoped route so membership cannot be probed by ID. Only administrators create projects and change assignments.
- All workspace state changes require CSRF and same-origin request validation. Public email unsubscribe is a separate recipient-owned POST authorized only by an unguessable scoped token; GET never changes preferences. The funnel open image is the one public GET that writes, and it only records an open event (see "Count opens").
- Provider keys stay server-side and encrypted at rest. Never add secret values to Vite define or VITE_ environment variables.
- AI provider settings (server/ai-settings.ts, shared/ai-providers.ts): a typed key is only sent to the providers its own format points to, or the one the administrator chose; a saved key is only ever sent to the provider and endpoint it was saved for (saving, testing and model listing all refuse otherwise). A listed provider always uses its own endpoint; only "Other" takes a typed base URL. Model listing never follows a redirect. Pasted keys are stored without whitespace. The connection status shown is the last check of exactly the saved setup and clears when the provider, endpoint, model or key changes.
- Fast decisions (server/jev.ts, server/quick-decision.ts, shared/quick-decision.ts): TypeSafe Jev on OpenRouter's Decisions API judges every published rule for a lead, or for an import row in the quick screen. The Jev key (an OpenRouter sk-or- key) is administrator-only, encrypted at rest, never returned, and sent only to OpenRouter's fixed Decisions address; it falls back to OPENROUTER_API_KEY, then a saved OpenRouter chat key. A quick decision is triage: it never sets a lead's status, score, decision or revision, it is stored separately with the lead revision and training version it judged (out of date once either changes), and the contact's name, email address and phone are never sent to Jev. A rule call needs 60% (an exclusion 70%), otherwise it is Unable to verify; the verdict follows the qualification's own score rule. Tests load tests/env.ts first, which clears provider keys from the machine so no test reaches a real provider.
- Public URL fetches must use server/network.ts, including validation on redirects and DNS pinning. Never send provider credentials over redirects or private-network endpoints.
- Uploaded documents are untrusted. Retain size, signature, ZIP expansion, page-count, timeout and process-isolation limits.
- Training analysis proposes rules; only explicit publication makes a version usable.
- Lead feedback is project knowledge, never an edit: it must not rewrite a stored run, a lead decision or a review. It invalidates the published training and is folded into the next published snapshot.
- Calling assignment never widens access: only an account that can already reach the project may hold one. Logging a call must not change the qualification, fit score or decision, and the call log is append-only.
- The manual lead status and comments are team bookkeeping: they never touch the qualification, fit score, decision, review or lead revision. Every status change is recorded (who, when, from, to), a stale change is refused, and a comment's text stays out of the audit log so deleting it really removes it. The Calls page and the lead list's Call status filter read one mapping (callOutcomeStage in shared/calls.ts).
- Email: a mailbox belongs to exactly one project (project_mailboxes, keyed by project_id). Reading, saving, testing and browsing it is administrator-only and project-scoped under /api/projects/:projectId/mailbox: 403 without the administrator role, 404 for a project the caller cannot reach. The password is encrypted at rest and never returned. Resolve the sender from the project that owns the lead; there is no workspace sender to fall back to, so a project without a configured mailbox simply cannot send. Treat the SMTP host as an outbound target — public addresses on a submission port only. Strip CR/LF from every header value, escape all body interpolation, keep a named sender and a working opt-out in every message, and record refused sends rather than discarding them. Never return a raw transport error.
- Funnels stay drafts until explicitly activated. Activation requires a public HTTPS origin and that project's own configured mailbox and copy address. Recheck membership, qualification, lead revision, recipient and suppression before delivery. Enrolled sequences cannot be edited. Pace due messages to one per minute per project (meta key 'funnel_last_tick:<projectId>') so one project's queue never waits behind another's, and never retry ambiguous SMTP acceptance automatically.
- "Stop the sequence when the lead replies" is a per-funnel option, on by default. Turning it off only lets an auto-matched reply leave the sequence running; a response recorded by a person, an opt-out, a bounce or archiving always stops it.
- "Count opens" (server/funnel-opens.ts) is a per-funnel option, on by default, that an administrator may switch at any time because it only changes messages not yet sent. Only funnel messages the delivery worker sends carry the 1×1 image, in their HTML part; individual mail and plain-text parts never do. Each message gets its own random 256-bit token, stored only as its hash with that message's project, lead and enrollment. GET /e/o/<token>.gif is public like unsubscribe, but it records an open event (first-open time and a count) and never a preference or anything else; every request — unknown, malformed, HEAD or rate-limited — gets the same no-store GIF, so a token's validity is never revealed, and no IP address or user agent is stored. Opens are approximate and the UI says so.
- Funnel counts are computed on the server once per enrollment, never per message: Sent and Follow-up from the delivery ledger under the sequence's own keys ('funnel:<enrollment>:<message>'; a sequence started from the composer was sent by definition), Opened from its open records, Replied from its status or a reply its own recipient sent after it joined, Bounced from its stop cause or a bounce of its address for that lead after it joined. Rates divide by the sequences sent. funnels.updated_at moves on an edit, a start or pause, the open switch and new enrollments, not on each send.
- A bounce stops every sequence for that address, suppresses it and marks the lead BOUNCED. A permanent SMTP refusal at send time counts; so does a delivery-status report from the project's own inbox, but only when it quotes a Message-ID that project sent and names that same recipient, so a report about the copy address never suppresses a lead.
- Email bodies from the rich-text editor are parsed through the shared allowlist (shared/email-html.ts) on the server whatever the browser sent, links are http(s) or mailto only, and merge values are inserted as text. Attachments and images are stored per project, limited in type (checked against the file's contents, not only its name), size and count, and sent as real attachments or inline cid images.
- Nothing is deleted automatically. Archiving (a score below 50, a closed company, or a stated reason) hides a lead from default lists and counts, stops its sequences and blocks sending, keeps the reason, and is reversible; bulk archiving shows the exact leads and refuses if that list changed before confirming.
- Deleting a project (server/project-delete.ts) is administrator-only and needs the project name typed exactly. A readable VACUUM INTO snapshot is written under the data directory first (no snapshot, no deletion; snapshots are never pruned automatically). Every row of the project goes in one transaction found from the schema itself, and foreign_key_check must show nothing new or it rolls back. The workspace-wide recipient history stays: email_deliveries, email_bounces, suppressions and unsubscribe tokens, detached from the deleted ids. It refuses while a delivery is sending or that project's inbox is being polled.
- Individual mail and funnels share a three-email recipient limit and durable suppression, including after lead deletion/reimport. Both are keyed by recipient address and stay workspace-wide: separate project mailboxes must never become a way to mail the same person again. Record outreach outcomes separately from qualification and preserve their append-only history. Explicitly enabled incoming IMAP sync may record matched replies; conversion and interest remain team decisions. Unsubscribe links stop future sends automatically.
- Incoming mail: administrator-only, project-scoped TLS IMAP configuration with encrypted credentials, public DNS pinning, read-only access, bounded messages and no raw transport logs. Recheck configuration revision and the enabling administrator before saving a sync. Each project keeps its own cursor and its own account key, so two projects pointed at one inbox keep separate histories — and each ingests its own copy of every message. Keep saying so: IncomingSettings.shared_with names the other projects already polling that inbox.
- Reply matching cannot cross the project boundary. Auto-matching considers only mail the polling project itself sent: match app-generated Message-ID references and the original sender, leaving ambiguous mail for explicit linking. Linking takes a lead_id alone and that lead must belong to the project whose mailbox received the message, so a reply never reaches a lead in another project. Inbox, Outbox, Sent and drafts are narrowed to the project and browsing them is administrator-only; the per-lead reply list stays open to project members. Preserve terminal outcomes and stop applicable queued follow-ups without changing qualification. Never render inbound HTML or fetch its images. A failing mailbox records its own last_error and is reported and skipped, because one bad provider must not pause polling or delivery for every other project. It does pause its OWN project's automatic deliveries: while an enabled inbox is failing, replies are not being ingested, so the "they already replied" stop cannot fire and a sequence would keep mailing someone who has asked to be left alone.
- A contact is personal data. Keep it only when the captured website evidence cited it, never from lead notes, earlier research or inference, and keep it erasable from the lead.
- Lead research (server/enrich.ts) researches only blank fields, from the company's own website, and may never invent one. A value is recorded only if the model quotes a sentence that is really on the fetched page AND that sentence contains the value itself: the page text is in the prompt, so quoting it is free, and a check on the quote alone lets an invented phone number ride in on a real "Contact us today". Phones compare digit by digit, a headcount needs a sentence about people, and a summary field needs most of its words in the quote.
- A website is never taken on the model's word and never verifies itself. A candidate domain is fetched through server/network.ts, must still be on the guessed domain after redirects (a for-sale page prints the very name being searched for), must not be a parked, for-sale or placeholder page, and must name the company in whole words — one shared common word is not identification. There is no search provider: when nothing verifies, say so and write nothing.
- Applying research is an ordinary recorded edit, made inside a transaction against a freshly read lead: never overwrite a value a person typed (while the pass was running or ever), always pass the same validators the lead form uses, bump the revision and clear the review so the previous verdict goes stale. A company detail (city, country, industry, employee count) filled by an import during the pass is research's to replace; a website or a contact never is. A discovered website that already belongs to another lead in the project refuses the whole run, because the record is probably a duplicate of that one.
- Field provenance (lead_field_history, server/field-history.ts, shared/field-history.ts): every write of a company detail (website, country, city, industry, employee count — never a contact, which is personal data) records the value it replaced, the new value and its origin: 'import' (insert and duplicate update), 'person' (the lead form, create and edit; only fields that changed) or 'research' (write-back and detail conflicts, with the quote and page). Research wins over imported data: it may replace a value whose latest origin is import or research, or one from the original record (no history; a research citation of the current value still counts as research), and never one a person typed. An import updating a duplicate may replace only an imported or original value, never a researched or typed one. The history is append-only, cascades with the lead and goes with project deletion. When the table first appears (meta key 'lead_field_history_v1'), a lead the audit log shows was created or edited on the lead form has its non-blank company details adopted as 'person' (an edit never said which field it changed), except values a research citation shows research wrote. The Company card shows the current value with "Verified by research", the quote and page under a separate "Source evidence", and the replaced imported value only inside "Original imported value", never beside the current one.
- Every applied value keeps its citation in lead_research_citations, so a contact on a record can always be traced to the page and sentence it came from. Erasing a lead's contact deletes its contact citations too, because the quote usually contains the personal detail. A later qualification run must never blank a contact already on the record.
- Qualification researches before it judges: a lead with blank researchable fields gets one research pass (server/lead-research.ts) before the evaluation, at most once per lead revision (lead_research_runs.result_revision), and the evaluation is told which details were entered in the record and which research found. A blank field is never evidence. Every approved rule must be evaluated as Meets / Does not meet / Unable to verify; a model that leaves rules out or cites ids that were never supplied is asked once more (one combined retry), naming them. Rules still missing after it save nothing; an id still invented is dropped, and a claim left with no source becomes Unable to verify with a visible gap, so the run is kept.
- Website discovery tries the business domain of the lead's contact email first. Free-mail and provider domains (isSharedMailDomain in server/enrich.ts) are never candidates, and the email-domain candidate is verified exactly like any other.
- People found on the company's own site live in lead_contacts. A row is kept only with a quoted sentence from a fetched page of the verified site that names the person; an email or phone stays only when that sentence prints it. Rows are erasable one by one or all at once, cascade with the lead, and never appear by name in the research log or the audit trail. The lead's primary contact columns are separate and are never replaced by them.
- A researched contact joins a running campaign as its own recipient (funnel_enrollments.contact_id; one enrollment per funnel, lead and recipient; one running sequence per address): the lead is held to every rule the primary contact is, suppression, bounces and the three-email limit are the contact's own address's, every merge field and step address must resolve to that person, and delivery rechecks the contact row and stops — never falling back to the primary contact — if the person was erased or their address changed. Erasing a contact stops their queued sequences in the same transaction and drops the address from any enrollment the email log does not already hold it for. A reply (where stop-on-reply is on) or an opt-out from anyone at the company stops the company's other sequences; a bounce stops only that address's.
- The server derives the outreach band from its own fit score. A stale or non-qualified lead has no outreach step, and a non-target keeps no call script.
- Qualification uses the approved snapshot and current lead revision. Validate every criterion/exclusion and source ID before saving. A citation is read back to a supplied id however it is written (case, brackets, "Source E2", the page URL or exact title) before it is judged invented. A Meets — criterion or exclusion — must cite at least one retrieved source: a fetched page (or the research findings), or the team's own imported list data, labelled as such (evidence kind provided_list, "Your lead list (provided data)", shown wherever sources are listed as "Your lead list" with no link, and described to the model as not checked on the web and good only for the facts it states). One citing only the lead record becomes Unable to verify with a gap. The opportunity summary is kept only with such a source. Contacts and detail conflicts stay website-only, and the unreadable-website blocker and the "No public website evidence" gap look at website evidence alone.
- The server computes the fit score (criteria met / all criteria × 100) and the final decision; the model's decision is advisory. In order: an exclusion met with a retrieved source (a page or the team's list data) → Not a target, score 0; any blocker → Needs review, score kept; otherwise 50–100 Qualified, 0–49 Not a target (qualifiedFloor in shared/types.ts). Blockers are only: a website on record none of whose pages could be read, with no other website evidence; a specific verification problem the model reports (another company, a shared name the evidence does not settle, a parked/for-sale/closed site, contradictory identity) — generic "missing information" blockers are discarded (specificBlocker in server/ai.ts); and, at 50 or more, an exclusion that could not be verified. Missing information only lowers the score and stays visible as gaps; confidence is reported, not used. Neither ever causes review.
- Service categories (rubric.categories: 0–12, names unique ignoring case) are part of the training: proposed by Train AI from the library, edited with the rules and only used once published with the version. A rubric or snapshot saved without them has none. Qualification rates every published category GOOD, POSSIBLE or NONE, matched to the training's names as rules are. GOOD and POSSIBLE need a retrieved source (a page or the team's list data) like a met rule; otherwise the rating becomes NONE with a gap. A category left out is NONE "Not assessed" and costs no retry; a lead that meets an exclusion keeps no service fit. Service fit never touches the fit score or the decision. leads.service_fit (server/service-fit-schema.ts) is the list's copy of the latest run's GOOD and POSSIBLE categories, written in the same transaction as the status and score, and goes stale with them: the Service fit filter matches current results only.
- Conflicting details: qualification may report that the company's own website states a different city, country, industry or employee count than the record. One is kept only when its record value is the lead's current value, the website value passes the lead form's validator, and its quote is really in the cited website evidence and contains that value (citationSupports in server/enrich.ts); anything else is dropped without a gap, one per field. The summary names both values instead of silently using one. Research wins over imported data: in the transaction that saves the run (applyFoundConflicts in server/detail-conflicts.ts), each kept conflict whose record value is still the lead's and was not typed by a person (see Field provenance) is written as the current value through the lead form's validator, with a lead_research_citations row, a 'research' history row and a lead.research_applied audit event; the conflict is stored marked applied, the revision moves once and the run is saved as current against the new revision (qualified_revision), because it judged with the website's value in front of it. A conflict over a typed value is never applied on its own: it stays visible beside that value, and only a person's "Use website value" (POST .../leads/:leadId/conflicts/apply) writes it, on the lead's latest run, against the revision they saw and while the field still holds the record value, as an ordinary recorded edit (lead.conflict_resolved) that leaves the run out of date.
- Never overwrite qualification history or the original AI result during human review.
- Training edits, lead edits and concurrent reviews must not be silently overwritten by in-flight analyses.
- Qualification jobs (server/qualification-jobs.ts) requalify many leads on the server through the same qualifyLead as the single-lead endpoint, never a second evaluation path. At most one RUNNING job per project (partial unique index) and one lead at a time per project. Project-wide scopes (stale, raw, stale_and_raw, all) are administrator-only because they spend AI credits on every lead; an explicit 'ids' list is open to project members, capped at 500 and filtered to the project. Archived leads are never included. The starter or an administrator can stop a job, which takes effect after the lead in progress. A job stops itself when the training changes (active version or revision), when its starter loses access, and after three provider-shaped failures in a row; a failure keeps a short reason, never the provider's own text. State lives in the database, so a running job resumes on restart; no timer may hold the process open, and tests step the runner (runNext/drain) instead.
- Research feeds qualification. A manual research pass on a lead without a current qualification says "· ready for qualification", and the lead page continues straight into the analysis, which reuses that pass (lead_research_runs.result_revision) instead of researching again.
- Import validation is atomic. Duplicate matching is confined to a project. CSV exports neutralize spreadsheet formulas.
- A lead, once in the project, is never lost or downgraded by running things again: re-importing a list never creates a second lead for a company and never touches a status, score, run or review (the preview shows the existing lead's status and score); a failed or stopped qualification saves nothing over the previous result; and a result superseded by a record or training change keeps its decision and score on show, marked out of date, instead of being blanked. Default lists hide only explicitly archived leads.
- List data (leads.list_data, server/list-data-schema.ts): an import keeps the columns no alias reads — an event, a funding round — as label → value, through one rule (listData in server/import.ts) whichever route it arrives by: at most 25 columns, 60-character labels, 300-character values, 4,000 characters in all. It never holds personal details: a column whose header names a person or a way to reach one is dropped, and so is any value with an email address, a phone-like run of digits (personalDetail in server/enrich.ts, dates and amounts aside) or a profile link. It is not part of leadSchema or the lead form, so an edit can neither send nor clear it; only the import path (file route, preview, chosen rows, quick screen) accepts it. Updating a duplicate merges it (a new value replaces the same column) and a change bumps the revision and clears the review like the other merged fields.
- The import quick screen (server/import-screen.ts, server/lead-import.ts) is advisory and reads row data only: the row's own fields minus the contact's name, email and phone, plus its list data (the uploader's own columns, shortened), against the published rubric — no source documents, no website fetching, no remembered facts. Every row is answered PASS, REJECT or UNCLEAR (rows left out after one retry that names them are "Not screened"), and a row already in the project never reaches the AI. Nothing is stored until the person chooses what to import; rejected rows are never stored (only their count reaches the audit log), and a passed row is not a qualified lead: the detailed, evidence-backed qualification is still required. Chosen rows go through importLeads, the same checks and transaction as the file import.
- Do not log raw provider errors, keys, complete prompts or uploaded document contents.

## Data and migration

- Active data: data/innovista.db and data/.innovista-encryption-key (both gitignored).
- Original sintertechnik.db is retained locally and read-only during the one-time migration. Do not delete it or its legacy encryption key.
- Migrated company rows retain legacy_json. Contacts, activities, notes and prior research have immutable project-scoped copies in preserved_research, displayed as reference material. Orders and all original records remain in the legacy database. Never overwrite existing lead edits or replace current decisions with historical ones during restoration.
- Mailbox adoption (server/mailbox-schema.ts, guarded by meta key 'project_mailboxes_v1') runs once and is additive: the old workspace SMTP settings are copied to every existing project so sending keeps working, while IMAP polling, if it was enabled at all, stays enabled for only the first project (lowest id), because two projects polling one inbox would each ingest a copy and show one project's replies to another project's members. That project also inherits the legacy IMAP cursor and the mail already received. The legacy settings rows ('smtp_%' and 'imap_config') are deliberately left in place, unread.
- Starter training: docs/sintertechnik-training.md, captured official website and a draft rubric requiring human approval.
- Environment settings: .env.example. Production requires HTTPS INNOVISTA_ORIGIN and a bootstrap token for remote setup.
- Tests must use disposable directories and deterministic AI/website fixtures. Never modify the user's real database to verify behavior.
